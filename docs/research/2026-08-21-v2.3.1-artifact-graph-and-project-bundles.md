# V2.3.1 artifact graph and project bundle decisions

## Question

How can CineWeave inspect cross-Skill dependencies, identify stale or broken
refs, answer approval questions and move a local project without introducing
implicit “latest” resolution, unsafe archive extraction or a second hidden data
model?

## Primary references

- [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) separates entities,
  activities, derivation, revision and provenance bundles. CineWeave borrows the
  entity/derivation/revision distinction, but does not claim complete PROV
  serialization compatibility.
- [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)
  binds an attestation to immutable subjects by digest. CineWeave similarly
  treats kind/ID/version/hash as one exact subject identity.
- [SLSA 1.2 artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts)
  requires matching the subject digest and checking provenance against explicit
  expectations. CineWeave therefore keeps content verification separate from
  gate policy: an intact artifact is not automatically approved.
- [Node.js file-system documentation](https://nodejs.org/api/fs.html) documents
  `lstat` for inspecting links and `rename` for path moves. The bundle workflow
  checks file types before reads and uses a same-parent staged rename after full
  project verification.

These are design inputs, not certifications. CineWeave hashes are not digital
signatures, and local approval records do not establish a cryptographic identity.

## Artifact graph model

Each immutable artifact envelope is a graph node. Any payload object containing
exactly `kind`, `id`, `version` and `contentHash`, with valid field shapes, is an
edge target. Discovery is structural so refs do not depend on property names
ending in `Ref` or `Refs`. The edge stores its RFC 6901 JSON Pointer location.

The runtime reports three integrity states:

- `resolved`: the exact target exists;
- `missing`: no artifact occupies the requested identity and version;
- `hash_mismatch`: the identity and version exist under a different immutable
  hash.

Version freshness is independent:

- `current`: no higher version exists for the same kind and ID;
- `superseded`: the exact artifact remains valid, but a higher version exists;
- `unresolved`: freshness cannot make an unresolved edge valid.

This avoids two dangerous shortcuts: silently redirecting an old ref to latest,
or treating a valid old version as corrupted. Strongly connected component
analysis remains a defense-in-depth check for malformed or legacy imports even
though content-addressed exact refs make honest cycles impractical to construct.

## Approval gate model

The latest decision for the same exact artifact ref wins. A V1 approval never
approves V2, and an approved decision followed by a later exact rejection is
rejected. Default gate requirements are:

1. the root exact artifact is approved;
2. dependency refs are resolved without hash mismatches;
3. the dependency closure is acyclic.

Two policies are opt-in because they change valid project behavior:

- `requireCurrent`: block a superseded root or dependency ref;
- `requireDependencyApprovals`: require approval for every resolved dependency
  in the selected closure.

Warnings and blocking reasons are separate machine-readable lists. An old exact
ref is a warning under default policy and a blocker only when currentness is an
explicit expectation.

## Project bundle model

V2.3.1 intentionally uses a directory bundle:

```text
bundle/
├── cineweave-bundle.json
└── store/
    ├── project.json
    ├── artifacts/...
    ├── approvals/...
    ├── idempotency/...
    └── executions/...
```

No generic archive is extracted. Every allowed regular file has a sorted entry
with a fixed category, safe relative POSIX path, byte length and SHA-256 digest.
The manifest has a canonical bundle hash over source-project identity, policy,
entries and summary. It also states:

```json
{
  "containsProjectContent": true,
  "redistributionAuthorized": false,
  "rightsApprovalImplied": false
}
```

Export first verifies the source project, rejects links and unsupported store
paths, writes a sibling temporary directory and renames it only after the
manifest validates. Import rejects links, backslashes, absolute/traversal paths,
duplicates, unknown categories, missing or unexpected files, digest or length
changes and any existing target `.cineweave` path. It copies verified bytes to a
temporary project, runs full project verification there and then renames only
the staged store into the target.

The transfer preserves V2.2 and V2.3.0 bytes exactly. It does not migrate,
rewrite approvals, imply publication rights or authenticate the sender.

## Rejected alternatives

- **Resolve every ref to latest:** breaks reproducibility and can apply an
  approval to unseen content.
- **Treat all old refs as invalid:** destroys legitimate historical and pinned
  production states.
- **Export a ZIP/TAR directly:** requires a larger extraction attack surface and
  platform-specific link handling before the core needs compression.
- **Overwrite an existing target store:** makes rollback and user-data ownership
  ambiguous.
- **Make SHA-256 equal trust:** digest integrity does not prove who produced or
  approved content.

## Verification obligations

The release gate covers graph summary consistency, exact gate decisions,
closure behavior, missing/hash-mismatch distinction, stale refs, deterministic
cycle components, project round trips, V2.2 preservation, byte tampering,
unexpected and duplicate files, path traversal, backslashes, no-overwrite and
CLI behavior.
