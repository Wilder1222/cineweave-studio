# V2.2 research decisions

This note records the evidence behind the V2.2 implementation so future changes
do not turn one observed failure into a universal Skill rule.

## Primary sources

- [OpenAI: Build skills](https://developers.openai.com/plugins/build/skills)
  defines a Skill around a recognizable user goal, explicit inputs/outputs,
  non-inference boundaries, representative activation tests and progressively
  disclosed references/scripts.
- [OpenAI: Package your plugin](https://developers.openai.com/plugins/build/plugins)
  treats the plugin as the stable distribution identity and supports Git-backed
  marketplace entries pinned by `ref` or `sha`.
- [OpenAI: Constructing evals](https://developers.openai.com/tracks/ai-application-development#constructing-evals)
  separates correctness checks from holistic rubrics and uses repeated evals to
  detect regressions and guide iteration.
- [RFC 8785: JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html)
  provides invariant JSON serialization for repeatable hashing and signing
  inputs.
- [wuyoscar/GPT-Image2-Skill](https://github.com/wuyoscar/GPT-Image2-Skill)
  demonstrates a useful separation between an agent Skill, an executable image
  CLI and a curated prompt gallery. Its gallery uses a small routing index and
  category files rather than loading the complete corpus for every request.

## Comparative findings

The GPT-Image2-Skill comparison reinforces four choices already present in
CineWeave and exposes one gap:

1. A high-signal routing index is more useful than a context-heavy image dump.
   CineWeave keeps its public atlas small and excludes media with unresolved
   redistribution rights.
2. Prompt craft and provider execution are different responsibilities.
   CineWeave's Prompt Skill remains provider-neutral; V2.3 should add adapters
   behind capability, cost, approval and receipt boundaries.
3. Domain patterns deserve progressive disclosure. CineWeave has domain recipes
   but still needs original, rights-cleared worked cases for product, food,
   architecture, editorial, diagrams and exact-text layouts.
4. Layout, literal copy, material, physical light and palette should be explicit
   controls rather than one style paragraph. These are separate Prompt blocks
   and owner paths in V2.2.

The inference is not that CineWeave should become a model-specific gallery or
copy the other repository's prompts. Its durable advantage should be the
contract graph, cross-skill ownership, continuity and evidence loop; a curated
case atlas should teach those mechanisms with original assets.

## Decisions

1. Keep the router optional; specialist Skills remain standalone.
2. Split general text-to-image Prompt management from directing because their
   triggers, inputs and success criteria differ.
3. Add Story as an independent semantic owner; Director consumes story intent
   and translates it into camera coverage.
4. Put hashing, storage, approvals and board composition in deterministic
   scripts rather than asking a model to reproduce mechanics.
5. Separate physical scene light, representational light grammar and photographed
   shot lighting instead of using one overloaded `lighting` field.
6. Keep provider adapters outside the core contracts and require capability,
   evidence, rights and human-approval gates before execution.
7. Exclude unverified user and third-party media from the distributable plugin.

## Evidence threshold

Schema and link validation prove package integrity, not Skill behavior. A release
therefore needs static gates plus fresh-task behavior samples. Live model runs
are recorded as test evidence but are never committed when they contain private
user media or credentials.
