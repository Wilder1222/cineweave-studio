# V2.3 research: execution evidence and live Skill evaluation

## Question

After V2.2 established eight standalone/composable Skills and an immutable local
store, the largest remaining gap was not another creative prompt template. It
was the boundary between a declared production plan and evidence that a known
implementation executed the exact approved request.

The second gap was evaluation. Static activation fixtures catch ownership and
contract regressions, but cannot show whether a clean Codex task actually finds
the intended Skill and returns useful bounded output.

## Primary-source findings

- OpenAI describes Skills as focused, repeatable workflows and recommends
  testing direct, indirect, incomplete, negative and edge triggering. Scripts
  are appropriate for deterministic processing. This supports keeping creative
  reasoning in Skills while moving execution and verification into runtime code:
  [OpenAI — Build Skills](https://developers.openai.com/plugins/build/skills).
- A plugin packages stable identity, Skills, MCP servers and resources. That
  supports a core plugin with provider-neutral contracts while allowing future
  provider bridges to arrive as separately trusted extensions:
  [OpenAI — Build plugins](https://developers.openai.com/plugins/build/plugins).
- OpenAI's evaluation guidance separates representative test data from explicit
  testing criteria and graders. This supports a versioned synthetic case set,
  strict response schema, deterministic grader and auditable run record:
  [OpenAI — Evals](https://developers.openai.com/api/docs/guides/evals).
- OpenAI recommends strict function schemas, including required properties and
  `additionalProperties: false`. The new adapter, execution and evaluation
  contracts follow the same fail-closed shape even though the local runtime is
  provider-neutral:
  [OpenAI — Function calling](https://developers.openai.com/api/docs/guides/function-calling).

## Decision: separate four layers

```text
creative facts and intent
          ↓
Production-authored execution intent
          ↓
trusted runtime implementation
          ↓
runtime-authored evidence
```

The resulting records have deliberately different authority:

- `CapabilityProfile` says what an adapter claims it can control.
- `AdapterDescriptor` identifies operations, limits, security policy and the
  hash of one trusted registry entry.
- `ExecutionRequest` binds exact inputs, mode, budget, idempotency key and
  authorization policy.
- `ExecutionReceipt` reports attempts, accumulated cost, failures and verified
  output bytes. A language model must not author it.

Contracts never contain a command, module path, endpoint, signed URL or secret
value. This prevents an authored JSON artifact from becoming executable code.

## Authorization model

Local dry-run and fixture modes deny external effects. External mode requires
both:

1. a human approval record bound to the exact stored `ExecutionRequest` hash;
2. explicit caller enablement at invocation time.

Either condition alone is insufficient. Rejection or a newer decision replaces
an earlier decision for the same exact request. A stable idempotency key may
bind only one exact request, preventing accidental replay against changed input.

## Cost and failure model

Unknown estimates block before execution. Every attempted provider call must
report its cost even when it fails. Retry receipts retain failed and successful
attempts in order; total cost must equal their sum and stay within the request
budget. Output files are constrained to the project execution root and verified
again during whole-project integrity checks.

The core ships only a network-free, zero-cost SVG fixture adapter. This proves
the protocol without normalizing credentials or paid calls into the base
plugin.

## Live evaluation design

The V2.3 smoke dataset contains synthetic requests for all eight Skills plus one
unrelated request that should activate none. Each case declares:

- expected Skill and route;
- acceptable owned contract kinds;
- forbidden Skills;
- deterministic text, question, outcome and safety checks.

Live mode runs each case in an isolated, ephemeral, read-only Codex task with
tools disabled by instruction and strict JSON output. It never runs by default:
the caller must name a model, acknowledge model costs and choose a fresh local
output directory. Before any model call, it verifies that the installed and
enabled plugin version matches the source package and that a Git install is
pinned to the corresponding immutable tag; this prevents a candidate run from
silently measuring an older cache. Raw events remain uncommitted. Release validation instead
grades committed, synthetic replay responses so CI is deterministic and free of
model cost.

`SkillEvaluationRun` preserves dataset hash, environment, per-case checks,
response hashes and aggregate rates. Semantic validation recomputes counts,
rates and the release decision so a plausible-looking summary cannot disagree
with its case evidence.

## Rejected alternatives

- **Let `RenderPlan` execute itself.** This mixes creative intent, provider
  implementation and evidence authority.
- **Store shell commands in adapter descriptors.** This turns data into an
  arbitrary-code channel and makes plugin review ineffective.
- **Treat a broad project approval as execution permission.** It cannot prove
  which prompt, adapter, budget or inputs were approved.
- **Run live models in every CI job.** This introduces nondeterminism, cost,
  credential handling and weak regression attribution.
- **Grade only with free-form model judgment.** A grader can drift. V2.3 starts
  with transparent deterministic checks; model-based quality graders can be
  added later as versioned, human-reviewed evidence rather than hidden truth.

## Next research priorities

1. artifact graph queries and stale exact-ref detection;
2. rights-aware local reference ingestion without public asset copying;
3. adapter conformance fixtures for cancellation, timeout and partial output;
4. versioned evaluation baselines and route-level regression comparison;
5. contract-aware one-variable repair execution with before/after evidence.
